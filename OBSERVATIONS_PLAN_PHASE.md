# BookShelf API - Project Observations and Plan

## Phase 1: Planning

### 1. Project goal

BookShelf API will be a small Java REST API for tracking books. Users will be able to
add books, view and filter their reading list, search by a partial title or author
name, update or delete books, and view basic reading statistics.

The implementation will use:

- Java and Spring Boot
- RESTful HTTP endpoints
- An in-memory `ConcurrentHashMap<Long, Book>` instead of a database
- A `BookRepository` interface with an in-memory implementation
- Spring Bean Validation for request validation
- JUnit and MockMvc for automated tests

The first version will focus on a clean and simple backend. A frontend is optional
and should only be added after the API is complete and tested.

### 3. Data model

#### `Book`

The stored domain model will contain these fields:

| Field | Java type | Required | Description |
|---|---|---:|---|
| `id` | `Long` | Generated | Unique identifier assigned by the service |
| `title` | `String` | Yes | Title of the book |
| `author` | `String` | Yes | Author of the book |
| `genre` | `String` | No | Genre, such as `fiction` or `history` |
| `rating` | `Integer` | No | User rating from 1 through 5 |
| `status` | `BookStatus` | Yes | Current reading state |
| `dateCompleted` | `LocalDate` | No | Completion date in ISO format |

`Long` will be used for IDs so the API has a stable numeric identifier. `Integer` is
appropriate for ratings because ratings are whole numbers. `LocalDate` represents a
calendar date without introducing unnecessary time or timezone behavior.

#### `BookStatus`

Status will be represented by an enum rather than a free-form string:

```java
public enum BookStatus {
    READING,
    COMPLETED,
    WISHLIST
}
```

This restricts status values to the three values required by the specification.

#### `BookRequest`

Create and update operations will use a separate request DTO:

```text
BookRequest
├── title: String
├── author: String
├── genre: String
├── rating: Integer
├── status: BookStatus
└── dateCompleted: LocalDate
```

The request DTO will not contain `id`. IDs are generated by the application and
should not be accepted from clients.

Validation rules:

- `title` must be present and must not be blank.
- `author` must be present and must not be blank.
- `rating` is optional, but when supplied must be between 1 and 5 inclusive.
- `status` must be present and must be a valid `BookStatus`.
- `dateCompleted` must be in the past or present when supplied.
- `dateCompleted` is strictly required when `status` is `COMPLETED`.
- `dateCompleted` must be absent when `status` is `READING` or `WISHLIST`;
  the request is rejected rather than silently retaining an inconsistent date.

Statistics will count completed books only when both the status is `COMPLETED` and a
completion date exists.

### 4. Endpoint plan

All endpoints will use the `/books` base path.

| HTTP method | Endpoint | Purpose | Expected success |
|---|---|---|---|
| `POST` | `/books` | Add a new book | `201 Created` |
| `GET` | `/books` | List all books | `200 OK` |
| `GET` | `/books?genre=fiction&status=COMPLETED` | Filter books | `200 OK` |
| `GET` | `/books/search?q=query` | Partial title/author search | `200 OK` |
| `GET` | `/books/stats` | Return reading statistics | `200 OK` |
| `GET` | `/books/{id}` | Retrieve one book | `200 OK` |
| `PUT` | `/books/{id}` | Update one book | `200 OK` |
| `DELETE` | `/books/{id}` | Delete one book | `204 No Content` |

The `/search` and `/stats` routes must be declared before the `/{id}` route or
otherwise handled so that the words `search` and `stats` are not interpreted as book
IDs.

### 5. Responsibility split

#### `BookshelfApplication.java`

Starts Spring Boot and provides the application entry point. It should not contain
book logic or endpoint code.

#### `Book.java`

Represents the stored book and the JSON response shape. It contains fields,
constructors, and accessors, but no HTTP or collection-management logic.

#### `BookRequest.java`

Represents incoming create/update JSON and owns field-level validation annotations.
Separating it from `Book` prevents clients from setting generated IDs and keeps
request validation independent from response representation.

#### `BookStatus.java`

Defines the allowed status values and gives Spring a type-safe way to parse the
`status` query parameter and request field.

#### `BookController.java`

Owns the HTTP layer:

- Maps URLs and HTTP methods.
- Reads path variables and query parameters.
- Applies `@Valid` to request bodies.
- Delegates operations to `BookService`.
- Returns appropriate success responses and status codes.

The controller should stay thin. It should not directly manipulate the in-memory
list or calculate statistics.

#### `BookService.java`

Owns application and business logic:

- Delegates storage to `BookRepository`; it does not own the collection.
- Creates, reads, updates, and deletes books.
- Applies optional genre and status filters.
- Performs null-safe, case-insensitive partial search against title and author.
- Calculates reading statistics.
- Raises a not-found error when an ID does not exist.

#### `BookRepository.java` and `InMemoryBookRepository.java`

`BookRepository` keeps storage separate from the service. The in-memory version
stores books in a `ConcurrentHashMap<Long, Book>` for quick ID lookup and uses
`AtomicLong` to create IDs safely. It does not need method-level `synchronized`
blocks.

#### `ApiExceptionHandler.java`

Provides consistent error responses across the API:

- Invalid request body or field validation → `400 Bad Request`
- Invalid enum/query parameter → RFC 7807 `ProblemDetail` with `400 Bad Request`
- Jackson enum parsing failures, such as an invalid `status`, → `400 Bad Request`
- Missing book ID → `404 Not Found`

Example error response:

```json
{
  "error": "book not found"
}
```

#### `BookshelfApplicationTests.java`

Tests the API through MockMvc so routing, validation, service behavior, and JSON
responses are checked together. At least five tests are required; the planned suite
will cover more than five behaviors.

### 6. Search behavior

`GET /books/search?q={query}` will search both `title` and `author`.

The search will be:

- Case-insensitive
- Partial, using substring matching
- Applied to either title or author
- Returned as a list of matching books

For example, a book by `Frank Herbert` should match `herb`, `Herb`, or another
substring contained in the author name. The same behavior applies to partial titles.

An empty, missing, or whitespace-only `q` parameter should be treated as invalid
input and return `400 Bad Request` rather than silently returning every book.

### 7. Filtering behavior

`GET /books` will support optional query parameters:

- `genre`: case-insensitive genre comparison
- `status`: enum value such as `READING` or `COMPLETED`

When both filters are provided, a book must satisfy both conditions. When neither is
provided, all books are returned.

### 8. Statistics design

`GET /books/stats` will return:

```json
{
  "totalBooks": 5,
  "countPerStatus": {
    "READING": 2,
    "COMPLETED": 2,
    "WISHLIST": 1
  },
  "averageRating": 4.25,
  "booksCompletedPerMonth": {
    "2026-01": 1,
    "2026-02": 1
  }
}
```

The calculation rules are:

- `totalBooks`: number of books currently stored.
- `countPerStatus`: count every valid status, including statuses with zero books.
- `averageRating`: average of books that have a rating; return `0.0` when no ratings
  exist, avoiding division by zero.
- `booksCompletedPerMonth`: group books with `status = COMPLETED` and a non-null
  `dateCompleted` by `YYYY-MM`.

### 9. In-memory storage approach

The repository will use a concurrent map and an atomic ID counter:

```text
ConcurrentHashMap<Long, Book> books
AtomicLong nextId
```

`BookService` will depend on `BookRepository` rather than directly managing storage.
No database, repository framework, migrations, or persistence configuration will be
added for this version. Data will be lost whenever the application restarts, which
is acceptable for the assignment.

Because a web server can process requests concurrently, the repository will use
thread-safe collection operations and `AtomicLong` ID generation instead of coarse
method-level synchronization.

### 10. Test plan

The minimum requirement is five unit tests. The planned tests are:

1. Create a valid book and verify `201 Created`, generated ID, and response fields.
2. Reject a request with a missing title using `400 Bad Request`.
3. Reject a rating below 1 or above 5 using `400 Bad Request`.
4. Reject an invalid or missing status using `400 Bad Request`.
5. Reject a completion request without `dateCompleted`.
6. Reject a non-completed request that supplies `dateCompleted`.
7. Reject a future `dateCompleted`.
8. List books filtered by genre and status, including records with null genres.
9. Search using a partial title and partial author name, including records with null
   searchable fields.
10. Reject missing, empty, and whitespace-only search queries.
11. Return `404 Not Found` for an unknown ID.
12. Update an existing book and verify changed fields.
13. Delete an existing book and verify it is no longer available.
14. Return total, status counts, average rating, and monthly completion statistics.
15. Return `averageRating: 0.0` when no books have ratings.
16. Return `400 Bad Request` with RFC 7807 `ProblemDetail` for invalid enum JSON.

Tests should reset the in-memory store between cases so results do not depend on
test execution order.

### 11. Error and HTTP status plan

| Situation | Response |
|---|---|
| Valid create | `201 Created` |
| Valid list, search, get, update, or stats | `200 OK` |
| Valid delete | `204 No Content` |
| Missing title or author | `400 Bad Request` |
| Rating outside 1-5 | `400 Bad Request` |
| Invalid status | `400 Bad Request` |
| Invalid date format | `400 Bad Request` |
| Future completion date | `400 Bad Request` |
| Missing completion date for `COMPLETED` | `400 Bad Request` |
| Completion date supplied for `READING` or `WISHLIST` | `400 Bad Request` |
| Empty or whitespace-only search query | `400 Bad Request` |
| Book ID does not exist | `404 Not Found` |

### 12. Implementation boundaries

The first implementation will not include:

- A database
- Authentication or authorization
- Pagination
- User accounts
- Complex sorting
- External book metadata APIs
- A required frontend

These are intentionally outside the scope so the core REST API remains simple and
testable.

### 13. Improvements over a minimal implementation

The basic requirement could be implemented with one controller and one list, but
this plan is easier to maintain because it:

1. Separating HTTP routes from business logic.
2. Separating request input from the stored response model.
3. Using an enum for valid statuses.
4. Keeps validation and error responses in one place.
5. Defining statistics output and edge-case behavior before coding.
6. Testing both success and failure paths.
7. Keeps storage behind a repository so it can be changed later.
8. Handles null search fields, no ratings, and date/status rules.

This adds useful structure without adding a database or extra framework code.

### 14. Gaps found and fixes in the final plan

The first plan missed a few important cases. These are now fixed:

| Problem in the first plan | Fix in the final plan |
|---|---|
| The service was planned to store books in a `List<Book>`. | `BookRepository` now handles storage, using `ConcurrentHashMap<Long, Book>` for quick ID lookup. |
| The plan relied on locking whole methods for concurrent requests. | The repository uses the thread-safe map and `AtomicLong`; no method-level `synchronized` methods are needed. |
| Searching or filtering a book with a null field could cause an error. | Searches and filters check for null values before comparing text. |
| Stats could divide by zero when no book had a rating. | `averageRating` returns `0.0` when there are no ratings. |
| A query made only of spaces could be accepted. | Missing, empty, and spaces-only queries return `400 Bad Request`. |
| The status and completion date rules were not fully defined. | A completed book must have `dateCompleted`; reading and wishlist books must not have one. The date cannot be in the future. |
| The rating range was not clearly enforced. | Ratings must be between 1 and 5 when provided. |
| A bad enum value in JSON could result in a server error. | `ApiExceptionHandler` returns a clear RFC 7807 `400 Bad Request` response. |
| The tests did not cover these edge cases. | The test plan now includes null fields, spaces-only queries, date/status rules, no ratings, and bad enum values. |

### 15. Planned implementation order

1. Create the Maven project and Spring Boot application entry point.
2. Add the `Book`, `BookRequest`, and `BookStatus` types.
3. Implement `BookRepository`, the concurrent in-memory repository, and CRUD logic in
   `BookService`.
4. Add controller routes for CRUD, filtering, search, and statistics.
5. Add validation and centralized exception handling.
6. Write and run the unit/API tests.
7. Document setup and example requests in `README.md`.
8. Consider the optional frontend only after the backend behavior is complete.
